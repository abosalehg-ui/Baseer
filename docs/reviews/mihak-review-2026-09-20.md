## 1. نظرة عامة سريعة

بَصير تطبيق سطح مكتب **محلي بالكامل** يحوّل مقاطع مرورية (داش كام، CCTV، سوشل
ميديا) إلى بيانات مخالفات منظَّمة قابلة للتحليل والتصدير. البنية خمس طبقات
واضحة: `app/ui` (PyQt6، RTL) → `app/workers` (QThread) → `app/core` (منطق
تطبيقي بلا أي استيراد من Qt) → `app/utils` → `app/config`، وعليها قاعدة DuckDB
محلية بسبعة جداول + سجل تدقيق.

**التقنيات**: Python 3.10+ · PyQt6 6.7 · DuckDB 1.1 · Ultralytics YOLOv8 8.3
(AGPL) · PaddleOCR 2.8 (مُقيَّد بـ`<3` عن قصد) · pyqtgraph · reportlab +
arabic-reshaper + python-bidi · pydantic-settings · PyInstaller + Inno Setup.

**حجم المستودع**: 134 ملفاً متعقَّباً، **17,121 سطر Python** (منها ~5,300 سطر
قابل للتنفيذ في `app/` و~4,200 في `tests/`). المراجعة غطّت كل ملفات `app/`
وملفات `scripts/` الحسّاسة (`download_models.py`, `check_structure.py`)
وإعدادات CI والتوثيق. لم أُراجع سكربتات PowerShell ولا `Baseer.spec` تفصيلاً.

**ما شُغِّل فعلياً في هذه المراجعة** (بيئة Linux + `QT_QPA_PLATFORM=offscreen`):

## 2. المراجعة التقنية والهندسية (45%)

### 2.1 البنية المعمارية وفصل المسؤوليات — **9/10**

فصل حقيقي لا شكلي: `app/core/` لا يستورد Qt إطلاقاً (تحقّقت)، الكواشف التسعة
كل واحد في ملف مستقل يرث `BaseViolationDetector`، والاستدلال نفسه مُمرَّر
كـdependency (`InferenceCallable`) فتُختبر الخدمة بلا torch. والحدود مفروضة في
CI لا مكتوبة في README فقط:

```python
# scripts/check_structure.py
LIMITS = (("app/core", 560, 95), ("app/utils", 400, 60),
          ("app/ui", 520, 110), ("app/workers", 300, 60))
```

الخصم الوحيد: طبقة العرض ما زالت تعرف تفاصيل الصفوف بالمؤشرات الرقمية في
`analysis_view._refresh_summary()` (`if c == 2: ... elif c == 6:`) بينما
`library.py` حلّ نفس المشكلة صح بـ`VideoDetails` المُسمّاة. أي `ALTER TABLE`
على ترتيب أعمدة `list_violations_for_editing` ينكسر بصمت هنا. **الحل**: أرجع
dataclass مثل `VideoDetails` من `list_violations_for_editing`.

### 2.2 قابلية القراءة والصيانة — **9/10**

أفضل ما في المشروع: التعليقات تشرح **«ليش»** لا «وش». مثال يستحق النقل:

```python
# app/core/db.py — transaction()
# تحذير: DuckDB يفرض القيود المرجعية عند الـcommit لا عند العبارة، فحذف
# صف أب وأبنائه داخل معاملة واحدة يفشل — استخدم autocommit المتتابع هناك
```

هذا النوع من التعليق يوفّر على المطوّر القادم ساعتين تشخيص. `mypy --strict` على
`app/core` مع استثناءات **مُبرَّرة بالاسم** لـ`app/ui` (stubs الـPyQt6 تُرجع
`X | None`) بدل `# type: ignore` مبعثرة.

# app/workers/runner.py
# نمط «أنشئ thread، انقل الـworker إليه، اربط ستّ إشارات» كان مكرّراً حرفياً...

**ج) كود ميت.** `PlaceholderTab` في `main_window.py` (~40 سطراً) لا يُنشأ في أي

### 2.4 معالجة الأخطاء والحالات الحدّية — **5.5/10**

هنا أخطر ما وجدته، وثلاثة منها من صنف «الإصلاح طُبِّق في مكان ونُسي في مكان».

**🔴 (أ) `frame_stride` يُفسد حساب السرعة بمعامل الـstride نفسه.**

الواجهة تعرض الخيار للمستخدم صراحةً:

```python
# app/ui/annotator_view.py
self._stride_spin.setRange(1, 30)   # frame stride
...
frame_stride=int(self._stride_spin.value()),
```

والمحلّل يحفظ أرقام الإطارات الحقيقية والتوقيتات الصحيحة:

```python
# app/core/analyzer.py — _default_inference
real_frame_no = kept_idx * stride
```

لكن حساب السرعة يفترض أن كل مركزين متتاليين تفصلهما **إطار واحد**:

```python
# app/utils/geometry.py — speed_from_centers_kmh
n_intervals = len(centers) - 1
dt_s = n_intervals / fps          # ← fps المقطع الحقيقي، لا fps/stride
return (total_px * meters_per_px / dt_s) * 3.6
```

وفي `extract_violations` يُمرَّر fps المقطع الخام:
`actual_fps = self._fps_for_video(video_id)`.

**أثبتُّ الأثر بالتشغيل** (مركبة سرعتها الحقيقية 54 كم/س، `fps=30`،
`meters_per_px=0.05`):

```
true          : 54.0
stride=1 calc : 54.0
stride=5 calc : 270.0      ← ×5
```

النتيجة: بـ`stride=5` كل مركبة تُصنَّف «سرعة زائدة» (الحد 80)، و
`FollowingDistanceDetector` يتأثر مرتين (يستدعي نفس الدالة لسرعتي المتبوع
والمتبوِع ثم يبني TTC عليهما). ولا يوجد اختبار واحد يمرّر stride≠1 عبر مسار
السرعة — لهذا مرّ الخطأ عبر 337 اختباراً.

**الحل** (في `app/utils/geometry.py` + الكواشف): احسب الزمن من الـtimestamps
المخزَّنة لا من عدد الفواصل. أضف دالة:

```python
def speed_from_track_kmh(detections, meters_per_px: float) -> float:
    """السرعة من (المسار بالبكسل ÷ الزمن الحقيقي من timestamp_ms)."""
    if len(detections) < 2 or meters_per_px <= 0:
        return 0.0
    dt_s = (detections[-1].timestamp_ms - detections[0].timestamp_ms) / 1000.0
    if dt_s <= 0:
        return 0.0
    centers = [bbox_center(d.bbox) for d in detections]
    total_px = total_path_length(centers)
    return (total_px * meters_per_px / dt_s) * 3.6
```

واستدعِها من `SpeedingDetector` و`FollowingDistanceDetector` بدل
`speed_from_centers_kmh(track.centers, fps, ...)`. وأضف اختباراً حارساً: نفس
الحركة بـ`stride=1` و`stride=5` يجب أن تُعطي نفس السرعة ±5%.

> ملاحظة مرافقة من نفس العائلة: `HighBeamDetector` يفلتر بـ
> `det.frame_no % self._sample_every_n_frames != 0`. مع `stride=3`
> و`sample_every_n=5` تصير العيّنة مضاعفات 15 فقط (سُدس المعدّل المقصود). عدّل
> الفلترة لتعمل على **ترتيب** الكشف داخل الـtrack لا على رقم الإطار المطلق.

**🟠 (ب) نفس خطأ فقدان البيانات الذي أُصلح في المخالفات ما زال قائماً في
الكشوفات.** CHANGELOG يقول صراحةً إنه أُصلح:

> «**فقدان بيانات صامت عند فشل الاستخراج.** `DELETE` ثم `INSERT` كانا بلا
> معاملة… أُضيف `Database.transaction()` ولُفَّت العملية به.»

وفعلاً `extract_violations` ملفوفة. لكن `_store_detections` ليست:

```python
# app/core/analyzer.py — _store_detections
self._db.execute("DELETE FROM detections WHERE video_id = ?", (video_id,))
rows = [...]
if not rows:
    return
self._db.executemany("INSERT INTO detections ...", rows)
```

أي فشل في `executemany` (قرص ممتلئ، صف تالف، إلغاء) يترك المقطع **بلا كشوفات
بعد حذف القديمة** — ومعه تضيع كل tracks المقطع. وقائمة التحقق في
`.github/pull_request_template.md` تنصّ حرفياً: «الكتابات متعددة الخطوات داخل
`db.transaction()`». **الحل**: لفّ الحذف + الإدراج + تحديث الحالة في
`with self._db.transaction():` كما في `extract_violations`.

**🟠 (ج) إخفاقات التحليل تُبتلع، بينما إخفاقات الاستخراج تُعرض.**
`analysis_view` يعمل الصح تماماً: يُجمّع الإخفاقات ويعرضها في
`_show_failures()`، ويشرح «صفر مخالفة» في `_explain_zero_violations()`. أما
مسار الاستدلال فيفقد الخبر:

```python
# app/workers/inference_worker.py
except Exception as exc:  # noqa: BLE001
    logger.exception("فشل تحليل المقطع %d: %s", vid, exc)
# ← لا تُجمَّع ولا تُرسَل مع finished
self.finished.emit(results)      # النتائج الناجحة فقط
```

فمستخدم يُشغّل الاستدلال على 50 مقطعاً ويفشل 20 منها (موديل ناقص، ملف محذوف،
CUDA OOM) يرى «تم» ولا يعرف أي مقطع سقط. **الحل**: غيّر إشارة `finished` إلى
`(results, failures)` مثل `finished_all` في `_ExtractWorker`، واعرضها بنفس
`QMessageBox.warning` المستخدم في `_show_failures`.

**🟠 (د) الإغلاق أثناء عمل عامل يقطع القاعدة من تحته.**

```python
# app/ui/main_window.py — closeEvent
reset_database_singleton()       # يُغلق الاتصال
super().closeEvent(event)
```

ولا يوجد `closeEvent` في أي view (تحقّقت بـgrep: `closeEvent` موجود في
`main_window.py` فقط)، فلا أحد يُلغي العامل ولا ينتظره. النتيجة عند الإغلاق
أثناء استيراد/استدلال/تدريب: استعلامات على اتصال مُغلق داخل thread، و
`QThread: Destroyed while thread is still running`. **الحل** في `closeEvent`:
اسأل الviews عن عمّالها، `cancel()` ثم `wait(5000)` (المقبض
`ThreadHandle` يوفّر الاثنين أصلاً)، واعرض «جارٍ إنهاء العمليات…»، وبعدها فقط
أغلق القاعدة.

**🟠 (هـ) «التكرار التام» مبني على hash جزئي.** `file_hash` يُلخّص أول 4 م.ب +
آخر 4 م.ب + الحجم فقط (موثَّق في docstring بأمانة)، لكن المستدعي يعامله دليلاً
قاطعاً و**يُسقط الملف تلقائياً**:

```python
# app/core/library.py
def _is_exact_duplicate(self, fhash: str) -> bool:
    """يفحص التكرار الثنائي الحقيقي (file_hash) فقط — أساس الإسقاط التلقائي الآمن."""
```

مقطعان بنفس الحجم ونفس الترويسة/الذيل (شائع جداً في تصدير دفعة واحدة من نفس
الكاميرا أو نفس أداة القص) يُعاملان «مكرَّرين» ويُرفَض أحدهما بلا مراجعة —
فقدان دليل في تطبيق مادّته الأدلة. **الحل**: إمّا اسمِّ العمود والدالة
`file_hash_partial` وحوّل المطابقة إلى `detect_duplicates()` للمراجعة البشرية
(كما يفعل phash بحكمة)، أو أكّد التطابق الجزئي بـhash كامل قبل الإسقاط (يُحسب
مرة واحدة فقط عند الاشتباه، فالتكلفة مقبولة).

**🟡 (و) `assert` كعقد تشغيلي في 8 مواضع** (`library.py`, `zones.py`,
`speeding.py`, `following_distance.py`, و3 في `evidence_dialog.py`). تُحذف كلها
بـ`python -O`، فينكسر السلوك بصمت في أي بناء مُحسَّن. **الحل**: استبدلها
بـ`if x is None: raise RuntimeError(...)` في الكود التطبيقي (أو
`typing.cast` حيث الغرض إسكات mypy فقط).

### 2.5 الأداء واستهلاك الموارد — **6/10**

**🟠 (أ) N+1 على الـmain thread في تبويب التحليل.** `refresh()` يستدعي
`readiness()` لكل صف:

```python
# app/ui/analysis_view.py — refresh()
for r, row in enumerate(rows):
    ...
    readiness = self._service.readiness(int(row[0]))
```

و`readiness()` يُنفّذ في كل نداء: استعلام zones + استعلام معايرة + عدّ
الكشوفات المتعقَّبة + عدّ الكشوفات + `Path(filepath).exists()`. أي **5 عمليات
I/O × عدد المقاطع**، في الـUI thread، بعد كل استخراج وكل تعديل وكل حذف. مكتبة
500 مقطع = ~2500 استعلام + 500 stat على القرص لكل تحديث. و
`_explain_zero_violations()` يعيد الكرّة على **كل** مقاطع المكتبة مرة أخرى.

**الحل**: أضف `AnalyzerService.readiness_bulk(video_ids) -> dict[int, VideoReadiness]`
بأربعة استعلامات مجمَّعة (`GROUP BY video_id`) لا 5N، وشغّلها في العامل أو في
`QThreadPool`، وخزّن نتيجتها في الذاكرة حتى التغيير التالي.

**🟠 (ب) التصدير كله في الـmain thread.** `_on_export` في `dashboard_view`
يبني الدراسة ويقرأ **كل** المخالفات بلا حد (`list_violations()`) ويولّد
PDF/Excel داخل معالج الزر. كل عملية ثقيلة أخرى في التطبيق في QThread (وREADME
يعلن ذلك كمعيار جودة) — إلا هذه. النتيجة على قاعدة بعشرات الآلاف من الصفوف:
نافذة «لا تستجيب» بلا شريط تقدّم ولا إلغاء. **الحل**: `ExportWorker(QObject)`
يُشغَّل بـ`run_worker` مع تقدّم وإلغاء، والزر يتعطّل أثناءه.

**🟠 (ج) تغيير فلتر الجدول يُعيد بناء كل الرسوم.**

```python
# app/ui/dashboard_view.py
self._filter_type.currentIndexChanged.connect(self.refresh)   # refresh = KPIs + رسوم + جدول
```

و`refresh()` يستدعي `_refresh_charts()` الذي يحسب `violations_by_type` +
`violations_by_hour` + `violations_heatmap` (استعلام تجميعي بـJOIN) ويحذف
ويُنشئ ثلاث ودجات pyqtgraph — رغم أن الفلتر لا يؤثر على الرسوم إطلاقاً (الرسوم
لا تستقبل الفلاتر). **الحل**: اربط الفلاتر بـ`_refresh_violations` فقط، واحتفظ
بـ`refresh()` لزر «تحديث» وللاستدعاء الأول.

**🟡 (د) لا حدّ على ما تعرضه المكتبة.** `LibraryView.refresh()` ينادي
`list_videos(...)` بلا `limit` (الخدمة تدعمه)، ثم `ThumbnailGrid.set_cards`
يجدول مهمة تحميل لكل بطاقة ويُبقي `QPixmap` 240×135 لكل واحدة في الذاكرة.
لمكتبة بالمئات هذا مقبول (المعلَن في README)، وللآلاف يصير مئات الميغابايت.
**الحل**: مرّر `limit=` مع ترقيم صفحات أو تحميل عند التمرير.

**ما أحسبه للمشروع هنا**: تحميل الصور في `QThreadPool` مع تحجيم خارج الـmain
thread، بناء التبويبات كسولاً، فلترة البحث داخل SQL مع debounce 250ms،
ومعالجة `HighBeamDetector` إطاراً واحداً في كل لحظة بدل 11 ج.ب — كلها إصلاحات
حقيقية موثَّقة بسببها.

### 2.6 الاختبارات — **8/10**

**مُتحقَّق منه بالتشغيل: 337 اختباراً تمر في 10.8 ثانية، تغطية 71%**، بما فيها
اختبار قبول E2E يمشي المسار كاملاً (استيراد → استدلال → استخراج → تصدير)
بمكوّنات محقونة، واختبارات ودجات حقيقية بـ`offscreen`، وبوابة
`--cov-fail-under=60` تمنع تسرّب التغطية.

الفجوات الحقيقية (من تقرير التغطية الفعلي):

| الملف | التغطية |
|---|---|
| `app/main.py` | **0%** |
| `app/ui/widgets/stats_charts.py` | 10% |
| `app/ui/trainer_view.py` | 13% |
| `app/ui/dashboard_view.py` | 14% |
| `app/ui/annotator_view.py` | 16% |
| `app/workers/inference_worker.py` | 38% |

`dashboard_view` عند 14% هو سبب عدم كشف ملاحظتي (ب) و(ج) في 2.5، و

```python
# scripts/download_models.py

```

مع `expected_sha256=None` يمرّ أي ملف يُسلّمه المسار (تسميم مرآة، وسيط
اعتراض، أصل مُختَرَق) ويُحمَّل بـpickle → تنفيذ كود بصلاحيات المستخدم. وإضافةً:
`if dest.exists() and not args.force: continue` يعني أن ملفاً استُبدل على القرص
لاحقاً **لا يُعاد التحقق منه أبداً**. **الحل**: شغّل `--print-hashes` مرة
وثبّت البصمتين في `MODELS`، واجعل الملف الموجود يُتحقَّق منه (احسب SHA256
للموجود وقارن بدل التخطي)، وأضف تحقق البصمة أيضاً عند **تحميل** النموذج في
`analyzer._default_inference` لا عند التنزيل فقط.

**الحساب صراحةً**: (7.5 × 0.45) + (7.5 × 0.30) + (7.0 × 0.25)
= 3.375 + 2.250 + 1.750 = **7.375 ≈ 7.4/10**

**قراءة الدرجة**: مشروع في الربع الأعلى من حيث الانضباط الهندسي — CI بستّ
بوابات حقيقية كلها خضراء عند التشغيل، تعليقات تشرح «ليش»، توثيق أرقامه صحيحة،
وقرارات خصوصية صائبة ومُعلَنة. ما يمنعه من الثمانية ليس الترتيب ولا النظافة
بل **صحة المخرَج**: كاشفان من التسعة يُنتجان أرقاماً خاطئة عند إعداد تعرضه

## ما لم أستطع تقييمه من الكود وحده

بأمانة، هذه لا تُعطى درجة:

- **دقة الكواشف فعلياً** (precision/recall على مقاطع حقيقية). الكود يُنفّذ
  الخوارزميات المعلَنة، لكن هل `RedLightDetector` يخطئ عند وجود إشارة حمراء
  لشارع متقاطع في الكادر؟ منطقياً نعم (`red_frames` مجموعة عامة لكل الإطار
  بلا ربط بالمسار أو الاتجاه)، لكن حجم المشكلة يحتاج قياساً على بيانات موسومة.
- **معقولية السرعة والمسافة بعد إصلاح الـstride**: تحويل px→m بمقياس واحد
  ثابت للكادر كله يتجاهل المنظور، فالسرعة في أعلى الكادر تُقاس بمقياس أسفله.
  يحتاج homography (4 نقاط مرجعية) لا `meters_per_px` مفرداً — وهذا يُقاس
  ميدانياً بمقطع معايرة معروف، لا من الكود.
- **الإحساس بالأداء الفعلي على RTX 4070** ومدّة استدلال مقطع نموذجي.
- **سلوك التطبيق على Windows 11 المحزوم بـPyInstaller** (المسارات،
  `%LOCALAPPDATA%`، غياب stdout) — الكود يعالجها بوعي واضح، لكن التحقق يحتاج
  تشغيل المُثبِّت.
